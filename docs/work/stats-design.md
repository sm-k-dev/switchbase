# 집계 캐시 설계 (switch_rating_stats, 2단계)

작성: 아키텍트 / 2026-11-08 / 상태: **확정** (2026-11-08, 사용자 직접 답변 Q1~Q7)
기준: `docs/HANDOFF.md` §3 (`switch_rating_stats`: 평균값, 표본 수, 갱신 시각 / 평가 저장 시 이벤트로 갱신), §4 2단계 "집계", `docs/work/rating-design.md` §5.3, 현재 구현(`RatingRepository.summaryOf` 실시간 쿼리, `RatingSummary`)

## 1. 목표와 범위

포함
- 스위치별 집계 행 `switch_rating_stats`를 두고, 평가가 저장·수정·삭제될 때 갱신한다.
- 상세 화면의 요약은 캐시 행을 읽는다(평가 목록 조회 때마다 전체 집계를 다시 계산하지 않는다).
- 표본 수(회원 수)와 평가 건수, 평균, 갱신 시각을 저장한다.
- 기존 평가 데이터로 캐시를 처음 채운다.

제외
- 후기, 컬렉션, 신고 (다음 항목).
- 빌드 조건 필터로 평균 좁히기 (3단계). 이 항목의 집계는 빌드 조건 없이 스위치 전체 기준이다.

## 2. 현재 상태

- 요약은 상세 화면을 열 때마다 `rating` 테이블에서 실시간으로 계산한다(`summaryOf`).
- 평균은 평가 건 기준, `sampleCount`는 서로 다른 회원 수, `ratingCount`는 평가 건수다(`rating-design.md` §5.3).
- 데이터가 적어서 지금은 문제가 없다. 집계 항목의 목적은 평가가 많아져도 상세 조회가 가볍게 유지되게 하고, 평균과 표본 수를 한곳에서 관리하는 것이다.

## 3. 데이터 초안: `V8__create_switch_rating_stats.sql` (V1~V7 수정 금지)

```sql
CREATE TABLE switch_rating_stats (
    switch_id       BIGINT       PRIMARY KEY REFERENCES keyboard_switch (id) ON DELETE CASCADE,
    avg_sound       NUMERIC(4,2),   -- 소리 크기 평균(평가 건 기준). 평가가 없으면 NULL
    avg_fatigue     NUMERIC(4,2),   -- 피로도 평균
    avg_star        NUMERIC(4,2),   -- 별점 평균
    member_count    INT          NOT NULL DEFAULT 0,  -- 표본 수 = 서로 다른 회원 수 (§5 Q4)
    rating_count    INT          NOT NULL DEFAULT 0,  -- 평가 건수 (평균의 기준)
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

- 행이 없는 스위치는 "평가 없음"으로 본다(§5 Q6). 평가가 생기면 행을 만든다.
- 평균 저장 정밀도는 소수 둘째 자리이고, 화면은 소수 한 자리로 표시한다(기술 선택, 질문 아님).
- 기존 데이터 채우기는 V8 안에서 `INSERT ... SELECT`로 한다(§5 Q7).

## 4. 갱신 방식 (질문 대상)

갱신 대상 시점은 세 가지다: 등록, 수정, 삭제. 빌드를 바꾸는 수정도 평가 행의 값이 바뀌므로 갱신 대상이다.

갱신 계산은 **해당 스위치의 집계를 `rating`에서 다시 계산하는 방식**을 추천한다. 증분(이전 값을 빼고 새 값을 더하는 방식)은 수정·삭제 때 실수하기 쉽다.

## 5-1. 결정 적용 방식 (아키텍트 정리)
- 갱신 계산은 해당 스위치의 집계를 `rating`에서 다시 계산한다(증분 계산 안 함). 같은 트랜잭션 안에서 실행한다.
- 재계산 명령은 스위치 하나 또는 전체를 다시 계산하는 관리용 명령이다. 노출 방법(관리자 화면 버튼 또는 명령행)은 개발자가 고르고 보고한다. 주기 실행은 없다.
- `member_count = 평가한 서로 다른 회원 수`, `rating_count = 평가 건수`, `avg_* = 평가 건 기준 평균`.



**Q1. 갱신 방식 (HANDOFF "이벤트로 갱신")**
- (a) **같은 트랜잭션에서 동기 갱신** — *추천*. 평가 저장과 집계 갱신이 함께 성공하거나 함께 실패하므로 어긋남이 없다. 단점: 같은 스위치의 평가 저장이 몰리면 집계 행에서 잠금 경합이 생긴다(규모가 작으므로 지금은 문제가 되지 않는다).
- (b) **커밋 후 이벤트 비동기 갱신**(`@TransactionalEventListener`, AFTER_COMMIT). HANDOFF 문구에 가장 가깝다. 단점: 갱신이 실패하면 집계와 평가가 어긋나므로 재계산 배치가 필요하다.
- (c) 집계 갱신 없이 주기 배치로만 갱신. 단점: 평가 직후 화면에 반영되지 않는다.

**Q2. 캐시 지연 허용**
- (a) **즉시 반영**(평가 저장 직후 상세에 보임) — *추천*. (a)를 고르면 Q1도 (a)다.
- (b) 수 초에서 수 분의 지연을 허용한다(Q1 (b)와 맞음).
- (c) 하루 단위 지연을 허용한다(Q1 (c)와 맞음).

**Q3. 재계산 배치**
- (a) **관리용 전체 재계산 명령 한 개**만 둔다(어긋남 복구용, 주기 실행 없음) — *추천*.
- (b) 매일 새벽 주기 재계산 배치를 둔다.
- (c) 배치 없음. 어긋나면 평가를 다시 저장해서 복구한다.

**Q4. 표본 수의 정의와 표시**
- (a) 서로 다른 **회원 수**만 표시(N명) — 평균 기준과 달라 혼동 가능.
- (b) 평가 **건수**만 표시(M건).
- (c) **둘 다 저장하고 "N명 · M건"으로 표시** — *추천*. 이미 화면이 이 형식이라 바꾸지 않는다.

**Q5. 평균의 기준**
- (a) **평가 건(행) 기준** — *추천*. 현재 구현과 같다. 같은 회원이 빌드를 여러 대 평가하면 그만큼 반영된다.
- (b) 회원별 평균을 먼저 내고 그 평균들의 평균을 쓴다. 한 사람의 여러 평가가 한 표로 취급된다.

**Q6. 평가가 없는 스위치 표시**
- (a) **"아직 평가가 없어요"**, 평균 칸은 비움 — *추천*. 0점으로 보이면 나쁜 평가로 오해된다.
- (b) 평균은 "–", 표본은 "평가 0명 · 0건"으로 표시.

**Q7. 기존 데이터 초기 채우기**
- (a) **V8 마이그레이션에서 기존 평가로 한 번 채운다** — *추천*. 배포와 함께 끝난다.
- (b) 기동 시 한 번 재계산하는 코드를 둔다. 재기동마다 실행되므로 비추천.
- (c) 관리용 명령으로 수동 실행한다.

## 7. 테스트 목록 (초안)

- 평가 등록·수정·삭제 뒤 집계 행이 `rating` 전체 재계산 결과와 같다.
- 같은 회원이 빌드 두 대로 평가하면 `member_count`는 1, `rating_count`는 2.
- 평가가 없어지면 평균은 NULL, 건수는 0.
- 동시에 두 평가를 저장해도 집계가 두 건을 모두 반영한다(Q1 (a)일 때).
- 재계산 명령을 실행해도 값이 같다(멱등).
- V8 채우기: 마이그레이션 뒤 기존 평가 데이터의 집계가 정확하다.
- 상세 요약이 집계 행을 읽는다(평가 목록 쿼리가 전체 평가를 집계하지 않는다).

## 8. 열린 위험

- 동기 갱신(Q1 (a))은 같은 스위치에 평가가 몰리면 잠금 대기가 생긴다. 현재 규모에서는 문제가 아니다.
- 재계산 명령이 없으면 어긋남을 고칠 방법이 없다. Q3에서 최소 한 개는 두는 것을 추천한다.
